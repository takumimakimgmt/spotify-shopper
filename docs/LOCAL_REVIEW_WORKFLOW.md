# Review memory, playlist changes, purchase planning and local matching

## Remembered confirmations

A separate versioned record stores explicit user decisions. Automatic XML flags and evidence are retained. Confirmed ownership applies only to the conservative recording identity (recording/source ID plus full title and full artist metadata; album is included when no source ID exists). Version labels are never stripped for this identity. A different-version rejection applies only to the same recording, XML fingerprint, candidate and rules version. Confirmations can be forgotten individually. Full reset removes them; clearing analysis history keeps them. Storage errors do not claim a decision was saved, and malformed records are preserved rather than overwritten.

## Differences

Each completed analysis compares against its preceding saved result. Spotify track identity handles metadata edits; rows without a source ID use the conservative recording key. Reordering alone is not a change, and duplicate occurrences are counted. Counts include added, changed, removed, unchanged and rechecked rows. A different XML fingerprint or rules version marks otherwise unchanged rows for recheck. The default difference view can be turned off to review the whole playlist. Spotify still needs to be fetched to discover changes; this is not a background subscription or scheduled monitor.

## Combined purchase plan

Across loaded playlists, identical recordings are grouped and sorted by the number of distinct playlists they appear in. A repeated occurrence within one playlist counts once. Mix/version differences stay separate. A recording matched/confirmed owned or still unresolved in another loaded result is excluded from the plan. Store links remain searches, not verified offers or availability. Existing Buy Later entries migrate to the same conservative identity without discarding their fields.

## Browser matching

The normal browser flow fetches Spotify metadata only. XML parsing, library indexing and matching run locally, with the matcher in a dedicated Web Worker. Rechecks send no HTTP request. There is no silent server fallback when local matching is unavailable. Input remains limited to 50 MiB, 100,000 library entries, 10,000 requested tracks and bounded execution time. The former 3 MiB transfer ceiling does not apply to local matching because the library is not transferred. XML parsing still uses the browser main thread before worker matching; large documents can briefly pause the interface. Each worker is terminated after completion, cancellation, failure or a 30-second deadline.

Matching follows the existing Python rules: ISRC, compatible exact candidates, album review, then Python-compatible SequenceMatcher review at 0.92. Unicode casefolding is explicit, and all artist credits/version annotations are checked before exact confirmation. The local rules version is 4; existing v3 snapshots remain readable, and the first local analysis rechecks them. Local fingerprints identify the retained recording metadata, not raw XML containing paths/cues. No XML, local paths, library metadata or original filename is included in browser API requests. The old server endpoints remain available for compatibility but are not used by the browser flow.

## Verification

The synthetic/committed-golden comparison corpus is generated by scripts/generate-local-matching-corpus.py using the existing backend engine. It contains 242 matching scenarios, 42 normalization scenarios and 85 similarity scenarios (369 assertions), including remix conflicts, collaborators, original/extended formats, Unicode and SequenceMatcher's autojunk behavior. The corpus contains no user XML or private playlist data. Additional tests cover review memory, invalidation, changes, purchase grouping and the absence of XML network requests.

Local verification: 510 unit/integration/reference assertions pass, along with typecheck and lint. The original 2,302-entry user XML and 20-track playlist were also checked locally against the Python reference: every row's owned state, reason and candidate matched (11 matched, 9 not found). This private fixture check was temporary and is not committed. In an isolated Chromium session with synthetic Spotify responses, a real bundled Web Worker returned matched/not-found/review results, and a human confirmation survived reload. Browser network inspection showed GET health/playlist calls only; no XML endpoint or upload request. The local Vercel Analytics script returns 404 outside Vercel; this is unrelated to matching.

The synthetic browser workflow also verified that re-analyzing identical input reports three unchanged rows and the difference view hides them until Show all tracks is selected. Two loaded playlists sharing a missing recording produced one combined candidate, with both playlists listed. Human confirmations were forgotten through the UI without changing automatic matching evidence.
